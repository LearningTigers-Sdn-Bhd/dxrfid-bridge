# DXRFID Integration — Project Notes

Context dump for picking this project back up. Written after building and
testing a Python protocol/dashboard toolkit against a **simulated** reader —
no real RFID hardware has touched this code yet (hardware is still being
ordered as of this writing).

## The goal

Jesselton Pixel is integrating a DXRFID reader system with **EventzFlow**
(the client's own event platform, being built separately) for an event with
two RFID touchpoints:

1. **Registration desk** — a **USB** encoder/reader binds a blank RFID
   tag's factory UID to an attendee's record (see "How RFID attendance
   tracking works" below — writing to the tag is possible but not the
   recommended approach).
2. **Entrance/exit gates** — a fixed reader detects tags as attendees pass.
   Confirmed wiring: **coaxial cable** to the antenna(s) (RF only, not data)
   and **Cat5/Ethernet** to a laptop/device (this is the actual data link —
   **not USB, not WiFi**).

Both touchpoints need to get tag events into EventzFlow via its API.

## How RFID attendance tracking works (concepts for EventzFlow's data model)

This came out of a long Q&A working through what the hardware actually does
vs. what has to be built in software. Worth reading before designing
EventzFlow's tag/attendance data model — these aren't obvious and got
several details wrong on first pass in conversation before landing here.

**The UID is factory-burned, not generated by us.** Every RFID chip has a
permanent, globally unique serial number set at manufacture — the encoder
can only *read* it, never create or change it. "Encoding" in the industry
sense means *writing to a separate, optional area* of the chip (writable
user memory blocks) — completely distinct from the UID. The device is
called an "encoder" (not just "reader") because it's *capable* of that
writing, the same way a "DVD burner" is named for writing, not reading.

**Two ways to identify a person from a tag — pick one deliberately:**
- **Option A — UID-linking (recommended, and what this toolkit assumes)**:
  read the tag's existing factory UID, store `UID ↔ Person` as a row in
  EventzFlow's own database. No writing to the tag at all. Simpler, more
  private (a UID alone is meaningless without database access — unlike
  writing a name/ticket type directly onto an openly-readable chip), and
  handles badge replacement cleanly (see below).
- **Option B — write data onto the tag** (e.g. the person's own UUID, via
  `ISO15693_WriteAFI`/`WriteMultipleBlocks`): lets a gate resolve identity
  without a database round-trip, which is genuinely useful **only if gate
  network connectivity is unreliable** (offline fallback) or a gate needs a
  millisecond local accept/reject decision (e.g. a physical turnstile) using
  a coarse category flag (AFI byte: "VIP"/"Staff"/"General"). If you do
  write a UUID for offline resilience, store it as raw 16 bytes (not the
  36-character hyphenated string) — tag user memory is only a few dozen
  bytes — and never write actual PII (name, ticket details), since UIDs and
  written memory are both openly readable by *any* compatible scanner, not
  just yours.
- **Whichever you pick, the "who is this person" question still needs
  answering from somewhere first** — writing to the tag doesn't remove the
  need for a QR scan/lookup step, it just changes where the resulting link
  is stored (tag vs. database).

**Registration is inherently two physical reads, not one** (QR/ticket scan
to identify the person + RFID read/write to identify the tag), *unless* the
binding work is shifted to before the event: pre-bind tags to a known
attendee list in batch ahead of time, and check-in becomes genuinely
one-step (verify identity, hand over the already-bound badge — no live
encoding at all). If badges print on-demand during registration itself
(this project's case), two live touches are unavoidable each time — the
closest to "one step" is a badge printer with an *integrated* RFID
encoder, so identifying the person alone triggers an automatic
feed-encode-print sequence.

**Duration/attendance-day computation is 100% EventzFlow's job, not the
hardware's.** The reader only ever gives you `(UID, timestamp, gate)`
events. "How long was John in," "did he attend 3 days" — that's software
logic pairing up in/out events and counting distinct days, built entirely
on EventzFlow's side. Worth checking whether the actual reader model
supports built-in in/out direction sensing (the SDK header has
`GateModifyTrafficFlow`/`GateReverseDirection`/`MeetingGateTakeRecords`,
suggesting some models do this on-device) — if so, direction comes for
free instead of needing to be inferred from separate reader placements.

**Lost/replacement badges: never overwrite, always reassign, and enforce
"one active tag per person."** Model it as a one-to-many relationship —
one Person, many Tag Assignments over time — not a single mutable field:
```json
"tags": [
  {"uid": "uidA", "assigned_day": 1, "status": "revoked"},
  {"uid": "uidB", "assigned_day": 2, "status": "active"}
]
```
Attendance events always resolve through *whichever tag was active at the
time* — nothing is lost when a new tag is issued, you're adding a row, not
overwriting one. **Critical constraint: only one tag may be `status:
active` per person at any moment** — enforce this atomically (e.g. a DB
transaction that revokes-old-and-activates-new in one step), not just as an
application-level convention, or a bug elsewhere could leave two tags
simultaneously valid for one person. This also resolves the classic
"attendee brings the old lost badge back on day 3" scenario cleanly: the
default is the old tag stays revoked (safe — it might genuinely have been
stolen), and if it turns out to have just been misplaced, reactivating it
is a deliberate one-click staff action (which should also revoke whatever
newer tag was issued in the meantime) — not something the system should
ever do automatically just because a UID was previously seen.

**Other operational caveats worth planning for, not yet designed:**
- **Read reliability**: tag range/reliability degrades near metal or liquid
  (a badge pressed against a phone, wallet, or worn under a metal lanyard
  clip) — expect some failed taps in practice, not just in theory.
  Multiple tags close together (someone carrying two badges) can also
  cause ambiguous reads.
- **Tailgating**: a single reader can't tell two people walked through
  together on one tap — if headcount accuracy matters, this is a physical
  process problem (staff supervision), not something the RFID system solves.
- **Missed taps** (tap-in recorded, tap-out never happens — crowd, reader
  hiccup, person left through a different exit): EventzFlow's logic needs a
  graceful fallback (e.g. auto-close any still-"in" session at day's end)
  rather than letting a person's state get permanently stuck.
- **Timestamp source**: log events using the server's received-timestamp,
  not a client/device local clock, to avoid clock-drift inconsistencies
  across multiple gate machines.
- **Direction misconfiguration**: if entry and exit are separate physical
  readers rather than one direction-sensing gate, each reader's "this is
  IN" vs "this is OUT" role is a manual config choice on your side — a
  simple mislabeling would silently invert everyone's in/out history.
- **Privacy/compliance**: this system tracks individuals' physical
  movements/attendance duration — confirm what consent/privacy notice is
  needed for attendees (relevant under Malaysia's PDPA, given the event
  data seen in EventzFlow's API), and what the data retention policy is
  after the event ends.
- **Power/network resilience at gates**: these run unattended for the
  event's duration — worth a UPS/battery backup and a plan for what happens
  during a power or network blip (this is exactly the offline-resilience
  question from the UID/write-to-tag discussion above).
- **Physical security**: the registration PC and gate laptops themselves
  are a soft target — anyone with physical access to a gate laptop
  currently has full access to the dashboard (see "Access control" in
  Future plans below), and physical tampering with a reader/antenna could
  go unnoticed without the heartbeat/diagnostics we built actually being
  watched by someone.

## Where the vendor SDK lives

`D5XXX_DXRFID/` (this folder) is the unzipped vendor distribution — old and
new SDK generations, demos in half a dozen languages, a `D-Tool` config
utility, and two protocol/API docs (originally Chinese filenames, garbled by
a GBK-vs-UTF8 zip encoding mismatch on extraction):
- `高频读写器协议开发指南v1.9.doc` — the wire protocol spec (frame format, CRC, commands)
- `C API demo/C API说明文档.docx` — the C API function reference
- `new demo/example/c++/ECRFID.h` — the current-generation SDK header (real
  exported function signatures, used verbatim for `encoder_service.py`)

No macOS build exists anywhere in the vendor package (Windows `.dll` +
Linux `.so` only) — this constrains everything below.

## Confirmed hardware/RF specs (from the vendor docs, not a datasheet)

Pulled directly from the protocol doc and SDK header — flagging exact
source for each, since some of this only applies to one SDK generation.

**Physical connection interfaces** (all three, confirmed in both SDK
generations):
- Serial (RS232): default 38400 baud, configurable to 9600/19200/38400;
  1 start bit, 8 data bits; parity configurable None/Odd/Even (default
  Even); device address `0xFF` = broadcast
- USB (HID): older generation uses a fixed VID/PID (`0xFFFE`/`0x0091`);
  newer generation enumerates devices dynamically via
  `GetHIDDriverList()`/`GetHidConnectString()` instead of a fixed VID/PID
- Network (TCP/IP): default port `6688`; newer generation adds
  `NetworkDiscovery()` to auto-find readers by broadcast on the LAN

**RF output power**: adjustable 0–10W via a config register (value × 0.5W
— e.g. register `0x08` = 4W), **factory default is 4W**; a special value
`0x80` drops power below 0.5W. Antenna selection is a bitmask register —
confirms **multi-antenna-port reader models exist** in this product line,
with a command to open one specific antenna port.

**Tag/protocol support — this is where it gets important, read carefully:**
- The **older generation** (`高频读写器协议开发指南v1.9.doc` — literally
  titled "**High-Frequency** reader protocol guide") only documents:
  ISO15693 (main tag protocol — UID, DSFID, AFI, EAS, block read/write),
  ISO14443A (includes Mifare-style stored-value commands: authenticate key,
  "format wallet," "top-up," "backup amount" — suggests e-purse/stored-value
  card support, not just plain ID tags), and ICODE-specific extensions
  (NXP's ISO15693 tag family — SLI/SLIX/SLIX2 — password protect, EAS).
  **This generation is HF only** (13.56MHz-class, short range — realistically
  centimeters to maybe ~30–50cm with a larger panel antenna, not a
  walk-through-several-meters technology).
- The **newer generation** (`ECRFID.h`) has everything above **plus**
  `ISO180006C_ReadData`/`ISO180006C_WriteData` — **ISO/IEC 18000-6C is the
  UHF Gen2 standard (EPCglobal Class 1 Gen 2, 860–960MHz)**, a completely
  different frequency band with much longer range (meters, not centimeters).

  **⚠ Correction to earlier conversation**: it was stated fairly confidently
  earlier that "this system is HF, short-range only, no hands-free
  walk-through." That was based only on the older doc's scope. The newer
  SDK's UHF functions mean **the actual answer depends on which specific
  model number is being ordered** — if it's a UHF-capable unit, genuine
  hands-free walk-through detection may actually be possible after all.
  **This needs to be confirmed against the real hardware's datasheet/model
  number once known — do not assume HF-only without checking.**

**Gate/turnstile-specific hardware hooks** (`ECRFID.h`): `GateModifyTrafficFlow`,
`GateSetRelayStatus`, `GateReverseDirection`, `GateClearTrafficFlow`,
`MeetingGateTakeRecords`/`LibraryGateTakeRecords`/`MeetingGateTakeFlashRecords`
— confirms dedicated "gate" hardware SKUs exist with built-in in/out
direction sensing, onboard traffic counters, and even offline record
buffering (`TakeFlashRecords` reads records stored on the device itself,
useful if network was down — ties into the offline-resilience discussion
above). Worth checking whether the ordered reader is one of these
gate-specific models, since it changes how much logic EventzFlow needs to
build itself vs. gets "for free" from the hardware.

### `mock_reader.py`
A from-scratch reimplementation of the vendor's wire protocol, built by
reverse-engineering the doc (frame layout) plus the actual CRC16 lookup
table extracted from `libECRFID.so` via `nm`/`objdump` (confirmed as
standard CRC-16/ARC, poly `0xA001`, non-standard init `0xEEEE`). Listens on
TCP like a real network-mode reader would, answers ISO15693 inventory
(`0xFE`/`0x01`) with 1–4 randomized fake tag UIDs, and reader-info
(`0x78`/`0x00`) with a fake device string.

**Frame format** (confirmed from the doc, this is the actual protocol):
```
Host → Reader:   SOF(0xEC) Len ComAdr CmdType CmdCode Data...        CRC16(LSB,MSB)
Reader → Host:   SOF(0xEC) Len ComAdr CmdType CmdCode Status Data... CRC16(LSB,MSB)
CRC16 = poly 0xA001, init 0xEEEE, over [Len..Data] (SOF and CRC itself excluded)
```

**Known gap**: real network-mode inventory adds a 2-byte flow-control "Flag"
sequence number per tag (host must ack it) that the doc's tables were too
garbled to reverse-engineer confidently. `mock_reader.py` uses the simpler
base frame layout instead. **This is the single biggest unknown** — it's
unconfirmed whether a real reader will accept/expect the Flag variant. Only
testable once real hardware arrives.

### `web_client/server.py` — the actual dashboard, read this file first
Pure stdlib Python (`http.server`), no pip installs. Talks to whatever is at
the configured host:port using `mock_reader.py`'s protocol functions
(imported directly, not reimplemented) — meaning it was built to potentially
talk to a **real network-mode reader directly, without the vendor DLL at
all**, if our reverse-engineered protocol turns out to match. Untested
against real hardware.

Also runs three background threads:
- `heartbeat_loop` — pings the reader every 5s, auto-detects cable/power
  disconnects (tested by killing the mock reader mid-session — correctly
  logged "Broken pipe" as a cable/power issue)
- `auto_forward_loop` — polls the reader every 2s and auto-POSTs **new** tag
  sightings to the configured API URL
- Both share one TCP socket, serialized through `IO_LOCK` so their commands
  can't interleave and corrupt each other's responses (a real bug that would
  have appeared once both loops went live simultaneously — fixed proactively)

**Dedup/suppression logic**: `STATE["last_forwarded"]` tracks per-UID
timestamps; a tag re-read within `dedup_seconds` (default 5, configurable in
the UI) is counted as suppressed instead of forwarded. Verified directly
with a fixed repeating UID (not through the mock reader, which generates a
fresh random UID every scan — realistic for protocol testing, useless for
dedup testing).

**API integration**: every outbound call to the live server sets a normal
browser `User-Agent`. This isn't cosmetic — the real EventzFlow API is
behind Cloudflare, and Python's default `Python-urllib/3.9` User-Agent was
being hard-blocked (Cloudflare error code 1010) before any auth check even
ran. Confirmed root cause via direct `curl` vs `urllib` comparison. Fixed
and verified against the **real** EventzFlow endpoint (HTTP 200, real event
data returned) — this part is genuinely production-validated, not just
mocked.

Full endpoint list: `/api/status`, `/api/connect`, `/api/disconnect`,
`/api/settings` (GET+POST), `/api/inventory`, `/api/info`, `/api/test-get`,
`/api/test-post`, `/api/diagnostics`, `/api/encode`, `/api/log`, `/api/tags`,
`/api/forward-stats`.

### `web_client/index.html` — the dashboard UI
Two tabs: **Dashboard** (connection, mock actions, tags seen, encoder,
live-server test, auto-forward controls, activity log) and **Settings**
(API URL, auth header/value with a reveal toggle, content-type, encoder
helper URL). Every technical control has a custom hover/click tooltip (ⓘ) —
not the native HTML `title` attribute, which doesn't support click/tap and
was the source of an earlier bug report. Activity log renders in plain
English by default ("Found a tag — ID ...", "Asked the scanner: what tags
are nearby?") with raw hex tucked behind a per-line expandable toggle.
"Preview Raw Request" shows the exact HTTP request that would be sent, with
a checkbox to reveal or mask the credential in that preview.

### `web_client/encoder_service.py` — USB encoder helper, **never run on real hardware**
A `ctypes` wrapper around the vendor's real exported functions (from
`ECRFID.h`, not guessed): `GetHIDDriverList`, `GetHidConnectString`, `Open`,
`ISO15693_WriteAFI`, `Close`. Meant to run as its own small HTTP service
**on the Windows registration PC** (USB HID + the vendor DLL only work on
Windows/Linux, not macOS) — the main dashboard calls into it over HTTP so
staff only ever see one unified UI. Confirmed it fails *gracefully* on macOS
("requires Windows... cannot run on Darwin") rather than crashing — that's
the only thing that's actually been tested here.

### `web_client/mock_eventzflow.py`
Standalone fake live-server with a live web view (`localhost:9000`) that
logs every call it receives and visually flags duplicate UIDs arriving
within 5 seconds — for eyeballing whether the dedup logic is actually
working before pointing anything at the real EventzFlow API.

## How to run all of this

**Windows:** double-click `START-DEMO-no-hardware.bat` (fake reader + fake
server + dashboard) or `START-HERE.bat` (real hardware). Nothing to install
beyond Python itself — this is all standard library.

**macOS / Linux:** `bin/dev` starts the same three processes and stops them
all on Ctrl+C. Or run them individually:

```bash
# Terminal 1 — fake reader
python3 app/mock_reader.py --port 6688

# Terminal 2 — fake live server (optional, for dedup/spam testing)
python3 app/mock_eventzflow.py --port 9000

# Terminal 3 — the dashboard itself
python3 app/server.py --port 5050
```
Open `http://localhost:5050`. Connect to `127.0.0.1:6688`. Set the API URL
(Settings tab) to `http://127.0.0.1:9000/events` to test against the mock
live server, or to the real EventzFlow endpoint once you have credentials.

To test the USB encoder path (will fail gracefully without Windows/real
hardware): `python3 app/encoder_service.py --port 7000`.

## Big constraints to remember

- **⚠ Most of the vendor's Windows DLLs are DEBUG builds and will not load
  on a normal PC.** Verified by parsing the PE import tables of every `.dll`
  in this package:

  | File | Arch | Links | Usable on a clean PC? |
  |---|---|---|---|
  | `new demo/x64/ECRFID.dll` | x64 | `MSVCP140D` `VCRUNTIME140D` `VCRUNTIME140_1D` `ucrtbased` | ❌ **debug CRT** |
  | `new demo/x86/ECRFID.dll` | x86 | `MSVCP140D` `VCRUNTIME140D` `ucrtbased` | ❌ **debug CRT** |
  | **`new demo/x64/Release/ECRFID.dll`** | **x64** | `MSVCP140` `VCRUNTIME140` | ✅ **use this one** |
  | `C API demo/X64/EC_RFID.dll` | x64 | `MSVCP140` `VCRUNTIME140` | ✅ (older-gen API) |
  | `C API demo/win32/EC_RFID.dll` | x86 | none (static) | ✅ (older-gen API) |

  The `…D.dll` / `ucrtbased.dll` runtimes ship **only with Visual Studio** —
  they are explicitly *not* redistributable and are absent from the VC++
  Redistributable. Loading a debug-CRT DLL on a clean registration PC fails
  with `OSError: [WinError 126] The specified module could not be found`,
  which is misleading: the file *is* there, its dependencies aren't. The
  top-level `x64/` folder is the obvious place to look and is the wrong
  build — **always take `x64/Release/ECRFID.dll`** (same 82 exports).
  Requires the VC++ 2015–2022 Redistributable (x64) and **64-bit Python**
  (32-bit Python + x64 DLL = `WinError 193`).

- **The ctypes bindings in `encoder_service.py` are name-correct.** Also
  verified from the PE export table: all eight bound functions
  (`GetHIDDriverList`, `GetHidConnectString`, `Open`, `Close`,
  `GetDeviceInfo`, `ISO15693_WriteAFI`, `TagInventory`, `FreeHGlobal`)
  are exported as clean, undecorated C names, so `ctypes` resolves them by
  name. `ECRFID.h` declares `__stdcall`, and the code uses `ctypes.WinDLL`
  (stdcall) — correct. `Open.restype` is `c_void_p`, so the context pointer
  is not truncated on 64-bit. What is still **unverified** is runtime
  behaviour against real hardware: the `--model` string (defaults `D5200`)
  and the **UID byte order** (ISO15693 UIDs are commonly displayed reversed,
  so the UID shown by the gate may need flipping before being passed to
  `ISO15693_WriteAFI`).

- **No macOS build of the vendor SDK exists.** Everything USB/DLL-related
  must run on Windows (or Linux for the `.so`). On the M2 Mac used for this
  work, that means a VM — **UTM is installed** (free, `brew install --cask
  utm`), recommended as an **Ubuntu ARM64** VM for testing the gate-reader
  logic at native speed (no vendor DLL needed there), or a **Windows 11 ARM**
  VM (built-in x64 emulation) for anything touching `ECRFID.dll` or a real
  WinForms-style GUI later.
- **Three physical connection modes exist in the protocol**: serial (RS232),
  USB, and network (TCP, default port 6688). Confirmed for this project:
  registration = USB, gate = network/Ethernet (not WiFi — the coax cable is
  for the antenna, Cat5 is the actual data link).
- **Performance is not a real concern.** This is I/O-bound (waiting on
  sockets/HTTP), not CPU-bound — no case for a lower-level language on
  performance grounds alone. (A separate conversation explored C#/WinForms
  as an option for other reasons — vendor SDK compatibility, single-.exe
  distribution — but the decision was to **stay in Python** for now; see
  "Future plans.")

## Future plans / next steps, roughly in priority order

1. **When hardware arrives**: point `server.py` directly at the real gate
   reader's IP (instead of `mock_reader.py`) and see if it just works. If
   the Flag-field assumption was wrong, this is where it'll show up as
   parse errors or timeouts — will need packet-level debugging at that point.
2. **Test `encoder_service.py` for real** on the Windows registration PC
   with the actual USB encoder plugged in. Expect to find and fix real bugs
   here — this code has never touched real hardware.
3. **Build EventzFlow's actual ingestion API** (the client is doing this
   separately) and switch the dashboard's auto-forward target from
   `mock_eventzflow.py` to it, watching for duplicate/spam behavior first.
4. **Offline resilience** — right now a failed POST to EventzFlow just logs
   and drops the event. Needs a local retry queue so a network blip doesn't
   lose check-in data.
5. **Settings persistence across restarts** — currently settings live in
   memory + the browser's `localStorage`; a server restart without a page
   reload forgets the API key. Needs writing to a local config file instead.
6. **Access control on the dashboard itself** — right now anyone on the same
   network can open it and see/change the API key or trigger encodes. Fine
   for testing, not fine left running unattended at a live event.
7. **Package as a real desktop app** eventually (not urgent) — `PySide6` +
   `PyInstaller` was the direction discussed if/when this matters, producing
   a native-feeling `.exe`/`.app` instead of "open a browser to
   localhost." Build the Windows `.exe` from inside the Windows VM (PyInstaller
   doesn't cross-compile), build the Mac `.app` natively. A simple GitHub
   Releases + "Check for Updates" button was the discussed update mechanism
   (manual-trigger only, not auto-download-on-launch — event-day reliability
   matters more than update convenience).
8. **Auto-start / service wrapper** for both the gate laptop and registration
   PC, so the bridge software survives a reboot without someone remembering
   to open a terminal.
9. Multi-antenna handling — the protocol supports multiple antenna ports;
   not yet surfaced anywhere if the real deployment ends up using more than
   one antenna per reader.
